# 代码审查

目标是把“看起来对”变成“有证据是对的”。默认只读；用户明确要求修复时才改代码。

## 先定范围

- 工作区改动：`git status`、`git diff`，区分已暂存和未暂存；先确认没有会被覆盖的用户修改。
- 提交范围：`git diff <base>...<head>`、`git log`；PR 用 `gh pr view`/`gh pr diff`。
- 文件或目录：先列清单，再决定是否拆分并行。
- 范围不清时先问；不要用“顺便全仓库看看”代替用户指定的范围。

## 读证据

1. 读改动本身，再读完整函数/模块，最后读调用方和被调用方。只看 diff 容易漏掉上下文约定。
2. 搜索同一模式的其它调用点。一个修复只补了报告里那条路径，往往说明根因还在。
3. 检查配置入口、默认值、迁移/回滚路径和错误分支；这些地方最容易出现“主路径通过、边界崩溃”。
4. 能运行时运行最小复现或相关测试；不能运行时明确说明验证缺口。

## 审查维度

- 正确性：边界值、空值、并发/竞态、生命周期、幂等、状态机非法转移、错误被吞掉。
- 回归：旧数据/旧配置是否还能读；卸载或回滚后是否还能打开；升级是否需要迁移。
- 权限与信任边界：输入验证、授权检查、跨会话/跨插件边界、路径穿越、命令注入、日志泄密。
- 资源：无界增长、未释放的监听/句柄、超时与取消、重试风暴。
- 可维护性：只在明显增加缺陷风险时报告；不把风格偏好当缺陷。

安全类发现交给 `security-review` 的流程，不在这里重复展开。

## 验证发现

- 每条发现都要能回答：什么输入/状态、走到哪一行、产生什么错误结果。
- 对抗自检：假设自己错了，回到源码找反证；找不到反证再保留。
- 不确定的写成“待确认”，并说明缺什么证据；不要用肯定语气包装猜测。
- 多个独立视角（正确性、并发、回滚、权限）比同一个视角重复三遍更有效；范围大时用 `workflow` 按维度扇出，再对每条发现做反驳验证。

## 输出

按严重度排序，每条包含：

```text
[严重度] 一句话结论
位置：path/to/file.ext:123
触发：具体输入或状态
后果：错误行为/数据损坏/权限提升
证据：相关代码或测试输出（可截断）
建议：最小修复方向（可选）
```

- 没有发现时直接说“未发现可确认的问题”，并列出实际检查过的范围和未覆盖项。
- 不把测试通过当作没有缺陷的证明；也不把静态模式匹配当作漏洞。
- 用户没要求时不要顺手改代码、提交或推送。

## 本仓库补充

- 修改 `config/` 或源码后跑 `rtk proxy node --test test/portable.test.mjs`；完整回归用 `rtk npm test`。
- 部署相关改动先看 dry-run，确认不会覆盖用户配置或丢失备份。
- 检查仓库规则：无凭据、无个人绝对路径、无实际会话/记忆内容；新增本地包需同步 package/bundle/provenance/锁模板/漂移检查。
