# 日常精简 PTC 与按需增强

常规 `scripts/harness.mjs install` 部署两个桌面能力集合：

| Profile | 用途 | 默认加载 |
|---|---|---|
| `desktop` | 桌面应用日常入口，默认原生 PTC | 官方 base/web-app，原生预设与权限/取消/持久化，独立浏览器 |
| `enhanced` | 明确需要完整增强、旧 Workflow 停止/恢复时 | 原有协作、工作流、记忆、技能和界面增强 |

`headless` 使用原生无头配置。部署不迁移、重写或删除会话、记忆、工作流日志和浏览器登录资料；安装器先备份管理文件，原有 `rollback` 继续可用。

## 日常使用

完全退出并重开桌面应用，新会话默认选 PTC。Standard 仍是原生可选项。日常 profile 不加载本地 Ultracode、关联会话、自动记忆、Team、额外技能库与增强 UI；项目规则及原生技能发现机制保持原生行为。个人全局技能目录不被修改或删除。

## 按需使用完整增强

从匹配版本的 CLI 显式启动：

```sh
dsh --profile enhanced
```

这是同一 DSH_HOME 下的独立 profile。不要同时在两个入口执行同一历史会话。旧 Workflow 的 `/workflow resume`、停止锁和日志继续由 enhanced 中的原有实现解释；不要在日常模式把失败/停止的任务重新描述为“继续执行”以绕过恢复判断。默认入口没有伪造同名增强命令。

仓库 `config/desktop.*` 保留完整增强来源；`presets/daily/` 与安装器的 `renderDailyPlan` 负责精简入口。受管技能只部署到 `profiles/enhanced/agent-capabilities/skills/`，不会在日常模型上下文列出整套额外技能。

## 浏览器隔离与停止

两个 profile 都使用原生 MCP 的代理作用域：每个执行者有独立连接、临时浏览器上下文和独立输出目录。子代理不会继承父浏览器的页面、cookies 或截图目标；要复核页面，应重新导航到同一预览地址，而不是假设共享标签。

此方案解决不同执行者共享页面状态的冲突，不限制无关任务并行，也不新增任务调度器。单个执行者内部依赖页面状态的操作仍应顺序执行。自定义文件导出路径、服务端 unsafe 代码和权限升级被拒绝。

停止、错误、中断回合会关闭该执行者的浏览器连接；不自动重启或重放不确定操作。需要重新浏览时新建会话，其他执行者的独立浏览器保持可用。代理卸载和应用退出复用原生生命周期清理。正常成功回合可在同一会话继续使用自己的页面。

隔离浏览器不替代文件沙箱，也不阻止两个写入者通过文件或外部数据库产生冲突；并行实现仍需要独立 worktree 或明确的唯一写入者。

## 验证与回滚

- `npm test`、`node --test test/portable.test.mjs`。
- `scripts/test-daily-browser.cjs`：隔离 DSH_HOME 中真实模型驱动 Standard/PTC 导航、页面互不污染、导出拒绝、停止释放；需要已配置模型凭据，不复制凭据文件。
- 再用原生 persistence 冷读测试历史，不能只以工具返回成功判定验收。
- `scripts/test-preset-loading.cjs` 可在 enhanced profile 验证旧增强服务；Workflow 恢复单测继续运行。
- 安装先 dry-run，部署后 status；回滚只恢复受管文件，不删除会话与测试证据。

六组网页实验支持“精简默认”的方向，不证明所有可选增强无价值，也不保证每个任务一定提速。此次保留完整增强供明确任务使用。
